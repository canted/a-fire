# A Fire testing

Read [AGENTS.md](../../AGENTS.md) and the closest existing test before changing behavior. The frontend uses React Router v7 and SWR; shared UI components use the project's MUI/CSS Modules direction. Backend tests exercise NestJS services and Prisma/PostgreSQL behavior.

## Choose the execution path

Follow the [README setup](../../README.md#testing) for local environment files, separate databases, browser installation, and SMTP prerequisites.

| Command | Use |
| --- | --- |
| `pnpm test:prepare` | Validate the test database and apply committed migrations before standalone database-backed tests. |
| `pnpm vitest` | Run frontend/backend unit and integration tests. Includes real PostgreSQL tests. |
| `pnpm vitest tests/frontend/unit/utils/time.test.ts` | Run a focused existing suite. |
| `pnpm test --playwright-only` | Start and stop the managed test app, apply migrations, and run browser tests. |
| `pnpm test` | Run Vitest and Playwright against the managed test environment. |
| `pnpm playwright` / `pnpm playwright:ui` | Use an already running test stack for focused browser work. |

[server/runtime/test-environment.mjs](../../server/runtime/test-environment.mjs) owns test environment selection and database isolation. Reuse it instead of implementing another dotenv loader or bypassing its checks. Real database tests require a disposable database with a distinct `test` name segment, such as `afire_test`. Browser setup clears test data.

The managed launcher defaults to frontend port 5174 and API port 4100. It requires those ports to be available and supplies proxy/websocket settings. Export `TEST_FRONTEND_PORT` and `TEST_API_PORT` to change them. PostgreSQL and a local SMTP catcher run separately; real OTP and invitation requests still call the mailer.

## Browser tests

[playwright.config.ts](../../playwright.config.ts) owns browser projects, timeouts, artifact paths, and authentication dependencies. Its `setup` project runs [auth.setup.spec.ts](../../tests/e2e/auth.setup.spec.ts) before Chromium and WebKit. Keep this dependency rather than conditionally omitting storage state when a file is absent.

Use these maintained helpers:

- [fixtures/factory.ts](../../tests/e2e/fixtures/factory.ts): create realistic user, circle, board, post, and reply fixtures.
- [factories/index.ts](../../tests/e2e/factories/index.ts): defaults for generated Prisma factories; generation is configured in the Prisma schema.
- [fixtures/cleanup.ts](../../tests/e2e/fixtures/cleanup.ts): fixture cleanup and full authentication-setup reset.
- [fixtures/otp.ts](../../tests/e2e/fixtures/otp.ts): poll the database for the OTP generated by the real request.
- [auth.setup.spec.ts](../../tests/e2e/auth.setup.spec.ts): maintained UI login flow and saved session.

Group specs by feature under `tests/e2e/`. Exercise the real route, API, and authentication flow for browser integration coverage. Prefer accessible role/label queries and observable user outcomes. Let the runner's traces, screenshots, and videos diagnose failures; artifacts live under `tests/e2e/reports/`.

## Frontend Vitest tests

- Use React Router's `MemoryRouter` for component tests or `createMemoryRouter` with `RouterProvider` when route objects/loaders matter. For actual route wiring, see [routerSmoke.test.tsx](../../tests/frontend/integration/router/routerSmoke.test.tsx), which uses the production `createRouteObjects` export.
- Reuse the [application fixtures](../../tests/frontend/fixtures/appFixture.ts) and the existing [TestSWRProvider](../../tests/frontend/integration/auth/testProviders.tsx) where their contracts fit. Give each render an isolated SWR cache.
- Mock hooks when testing a component's response to loading, errors, permissions, or mutations. Include integration coverage through real hooks/API helpers when cache behavior or network contracts are the change.
- [frontend/site/lib/swrQuery.ts](../../frontend/site/lib/swrQuery.ts) exposes SWR wrappers with names such as `useQuery` and `useMutation`. These names do not imply TanStack Query; do not add QueryClient or TanStack routing examples.
- [vitest.setup.ts](../../vitest.setup.ts) owns shared browser polyfills. Extend the existing setup for a missing browser API instead of scattering global mocks across suites.

Storybook stories use production components and realistic typed fixtures. Supply a React Router wrapper for stories that navigate; global Storybook configuration does not add one. UI approval is followed by verification through the production route as required by AGENTS.md.

## Backend tests and file placement

Search both `tests/backend/<feature>/` and `tests/backend/unit/` before adding a service test; the repository currently contains both conventions. Extend the maintained suite for that behavior instead of creating a second file with the same role. Keep database-backed integration tests identifiable under `tests/backend/integration/`.

Mock service dependencies for unit tests and assert authorization, validation, returned data, and consequential jobs/events. Database integration tests use the validated test environment, clean up their own fixtures, and close Prisma/socket/server connections. Use real database tests when locks, transactions, constraints, or cross-process behavior are essential to the change.

Run the smallest relevant suite first. Broaden to affected integration/browser flows when a change crosses layers, and report any unexecuted checks with the actual reason.
